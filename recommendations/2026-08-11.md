# 采用建议 — 2026-08-11

## 1. 为高频 cron 建立精简的 Standing Orders
**优先级：高｜风险：低（先只写 workspace 指令，不改 scheduler）**

- **能力：**OpenClaw 的 Standing Orders 可放在自动注入每个会话的 `AGENTS.md`，将 scope、approval gate、escalation 和“不得做什么”与 cron 的触发时点分离。
- **场景：**当前 cron guide 把 isolated session 描述为无互动历史，因而 job prompt 常需完整复制规则；同时 workloop、巡检和 github-patrol 已反复执行同一套“证据不足不外发、不可逆操作须授权”边界。
- **建议：**先为 `workloop`、`channel-patrol` 和 `github-patrol` 写三个短 program：每项只含授权范围、不可逆操作审批、失败后最多一次调整重试与升级条件；cron prompt 改为引用对应 standing order。不要改变 schedule、delivery 或外部写权限。
- **验收：**从三个 isolated run 抽样，确认规则被加载、输出仍含可验证证据，且没有新增外部写入；对比 prompt 长度与遗漏的安全边界。
- **收益：**减少重复 prompt 与上下文漂移，使跨频道自动化的安全边界更一致、可审计。

## 2. 将 `daily-review` 的 preflight 与 delivery 分层
**优先级：高｜风险：低（先只读诊断）**

- **能力：**Task Flow / background task 的 durable state 可在 gateway restart 后保留；automation 文档也建议在 LLM 汇总前检查网络、凭据、工具与 failure destination。
- **场景：**本窗口的 `daily-review` 卡在 `model-call-started` 并缺少产物，且同一时段 Discord 有 READY timeout；当前状态不足以区分模型执行、网关或 announce delivery。
- **建议：**先在该 job owner context 做只读 run-history 诊断。若确认重复发生，再设计一个不写外部系统的 preflight（gateway/channel 可达、磁盘/swap、输入文件）和明确 failure destination；不要现在改 cron 或自动重跑。
- **验收：**一次失败可以被准确标为 preflight、agent execution 或 delivery，且 failure notification 有独立送达状态。
- **收益：**避免将一次通道故障误归因为任务逻辑，并让每日关键产物的缺失更早可见。

## 暂不采用
- **暂不立即升级 `2026.7.1-2`。**它只修复官方插件更新 metadata 兼容性；目前没有相应故障。放在受控插件维护窗口升级并验收。
- **暂不把所有 cron 改为 persistent session 或 Task Flow。**当前 isolated cron 并行工作正常；只应对需要累积上下文或多步骤可恢复状态的具体流程试点。
