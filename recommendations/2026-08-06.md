# 采用建议 — 2026-08-06

## 1. 在失败 cron 上试用 run-history 驱动的诊断
**优先级：高｜风险：低**

- **能力**：OpenClaw 的 cron 管理接口提供单 job 的 `runs` 查询，可读取运行历史，而不仅是 list 中最后一次的概览状态。
- **场景**：`close-prs` 的 upstream-comment 403 与 ABTI timeout 已知为阻塞，但频道摘要不足以判断它们是偶发、是否重试、以及 delivery 是否受影响。
- **建议**：先选一个非业务关键、已失败的 job，读取最近 10 次 run 的状态、错误、开始/结束时间和 delivery 结果；把原始证据写入其既有 TODO，再决定最小修复或降频策略。
- **验收**：能从 run history 区分“执行失败”“delivery 失败”“timeout”和“被跳过”，且不会改动 job 配置或重跑生产动作。
- **收益**：减少从 session transcript 猜错误根因的时间，并避免针对模糊摘要盲改 cron payload。

## 2. 为原生 Codex 后续处理建立 patrol → task-thread 引用
**优先级：中｜风险：低**

- **场景**：Cove #510 的冲突/反馈在多个 isolated cron 中被正确识别，但这些运行没有可调用的原生 Codex task-thread 入口。
- **建议**：在 patrol 的结构化状态或 TODO 中保存该 PR 对应 task thread 的稳定引用；下次发现同一 blocker 时只更新引用和证据，不再尝试从 isolated cron 重新执行代码工作。
- **验收**：频道摘要能给出一个明确的“在哪里处理”链接/标识；isolated cron 不产生重复 spawn、替代 harness 或无效重试。
- **收益**：保留权限边界，同时缩短人工或 task thread 恢复时的定位时间。

## 持续观察
- `2026.7.1-2` 仅修复 npm 官方插件 metadata 兼容性；仍建议等下一次官方插件变更或稳定版升级时一起采用。
- 对 dynamic cadence/trigger gate 的建议暂不直接改配置：先用 run history 确认重复阻塞的实际频率和错误类别。
