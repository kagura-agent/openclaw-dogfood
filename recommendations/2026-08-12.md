# 采用建议 — 2026-08-12

## 1. 为关键 cron 配置独立 failure alert 与分层 run-history triage
**优先级：高｜风险：低（先只读盘点与通知配置，不改变业务 prompt 或 schedule）**

- **能力：**OpenClaw cron 支持 job 级 `failureAlert`，并可读取每个 job 的 run history、last error 与 delivery 状态；这能把执行失败、通知失败和已恢复的历史错误分开。
- **场景：**daily-review 的原始 scheduler 证据显示 8 个 error-status job，但根因从 gateway restart 到模型超时、edge-tts、文件编辑失败不等；单一“error”标签不足以决定重跑。
- **建议：**先为 `daily-review`、`abti-loop`、`lottie-studio-loop`、`stocklingo-loop` 和 `coros-token-refresh` 建一张只读 triage 表：连续错误数、最近 run phase、是否有成功 recovery、delivery 状态。确认现有告警覆盖后，仅为没有可靠提醒的关键任务设置独立 failure destination 和合理阈值（例如连续 2 次失败）；不自动重跑，也不改外部写权限。
- **验收：**一次失败能被明确分类为 execution、delivery 或 gateway interruption；连续失败会有可见通知，而单次已恢复故障不制造噪声。
- **收益：**将“8 个 error status”转换为可处理优先级，减少盲目补跑和静默缺失。

## 2. 试点更精确的 memory retrieval contract
**优先级：中｜风险：低（先改 prompt/template，不动 runtime 或索引配置）**

- **能力：**`memory_get` 支持按确定路径和范围读取，`memory_search` 返回 source、行号和相似度信号；两者适合组成“精确读取优先、检索补充”的证据链。
- **场景：**memory-eval 已验证具体实体+独特事实检索稳定，但宽泛问题会命中陈旧日志和 dreaming 重复内容；这会让 cron 汇总的当前状态带入历史噪声。
- **建议：**为 channel-patrol、daily-review 和 dogfood 报告的 prompt 加一条短规则：已知日期/实体时先 `memory_get` 当日文件；仅在未知位置时 `memory_search`，且输出需引用日期/路径并将模糊命中标为待核验。先抽样三天，不修改 runtime retrieval 排序。
- **验收：**抽样报告不再把旧 dreaming 文本当作当前状态；每个跨日结论都有日期或原始 session/scheduler 证据。
- **收益：**以最小变更降低记忆污染，同时为日后 runtime 级 provenance 改进保留可比较基线。

## 暂不采用
- **暂不立即升级 `2026.7.1-2`。**其唯一变更是官方 npm 插件更新 metadata 兼容性；当前未复现相关故障，应在维护窗口受控验证。
- **暂不把全部 error-status jobs 自动重跑或迁移到 persistent session/Task Flow。**先以 run history 确认根因；隔离 cron 目前仍持续稳定地产出，错误类别并不一致。
