# 采用建议 — 2026-08-19

## 1. 给关键 cron 配置模型 fallback，终结 LLM idle timeout 盲区
**优先级：高｜风险：低-中（先试点 1 个 job，观察一轮再铺开）**

- **能力：**cron job 支持 `model` + `fallbacks`（模型回退列表）；watchdog 08-15/08-17 连续记录 floway-sg-deepseek 与 floway-jp-deepseek 双双 300s 无首 token（08-17 21:00 patrol `All models failed (2)`），近 7 天第 3 次同型。
- **场景：**夜间核心 job（daily-review / nightly-backup / channel-patrol）任一无首 token 即整轮失败、无产出，次日审计才发现。这是 provider 层间歇延迟，不是任务逻辑问题。
- **建议：**给 channel-patrol（最频繁、最依赖产出）试点加 fallback：主 floway-sg-deepseek → 备 floway-jp-deepseek 或本地备用 provider；同时确认 `timeoutSeconds` 上限不被 provider 空转吃掉。观察一轮（≥24h）无回归后，推广到 daily-review / nightly-backup。
- **验收：**一次 provider 无首 token 时 job 自动走 fallback 并正常产出，而不是 `All models failed`。
- **收益：**把「夜间 3/4 核心 job 超时」从已知痛点变成可自动恢复，减少每日审计擦屁股。
- ⚠️ 前置：fallback 配置涉及 openclaw 配置变更，按纪律先给 Luna 确认再动。

## 2. nightly-backup 的 exec timeout 基线固化（配置纪律）
**优先级：中｜风险：无（纯任务描述/文档）**

- **能力/场景：**04:15 nightly-backup 首次执行因 exec timeout=600s 被 SIGKILL，产出 6.8G 不完整文件；重跑 5400s 成功。备份任务实际需 20-25 分钟。
- **建议：**在 nightly-backup 任务描述中写入「exec timeout ≥3600s + 完成后必须 `gzip -t` 校验」，避免下个 session 再犯。
- **验收：**连续 3 轮 nightly-backup 无「超时中断/不完整产物」记录。
- **收益：**消除一类自伤型失败，备份可靠性可审计。

## 3. Cove 迁移收尾：多轮稳定后删 Discord 侧 cron 定义
**优先级：中｜风险：低（删除前先验证 Cove 侧 ≥2 轮正常）**

- **能力/场景：**server-health / github-check / email-patrol / email-dev 已迁 Cove（Discord 侧 enabled=false），但定义仍在 `~/.openclaw/cron/jobs.json`，双源并存有重新启用的误操作风险。
- **建议：**Cove 侧 github-patrol 跑满 2 轮、email-patrol 首轮（明天 09:58）通过后，删除 Discord 侧 4 个 cron 定义；#533 定点调度落地后把 Cove interval 改成精确定点。
- **验收：**`openclaw cron list` 不再出现已迁移 job；Cove recurring task 正常触发。
- **收益：**单一数据源，消除双跑/误恢复风险，符合「单一真相」原则（与 portable-self 同思路）。
