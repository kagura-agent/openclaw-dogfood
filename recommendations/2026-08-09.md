# 采用建议 — 2026-08-09

## 1. 小范围试用只读 `openclaw audit` 做 recurring-cron 取证
**优先级：高｜风险：低（只读 metadata 查询）**

- **能力**：`openclaw audit` 支持以 `--after/--before`、`--agent`、`--session`、`--run`、`--kind`（`agent_run`/`tool_action`）和 `--status` 过滤 bounded metadata JSON。
- **场景**：多个频道出现 “Agent couldn't generate a response”，而 `cron list` 曾超时；频道摘要不足以区分 agent execution、工具动作、delivery 或 timeout。
- **建议**：在拥有目标 cron 可见性的受控上下文，选择一个非关键失败 job，执行一次只读查询：`openclaw audit --after <ISO> --kind tool_action --json --limit 50`；仅保留脱敏 metadata 与结论，不重跑、不改 scheduler。
- **验收**：可关联 session/run、时间、工具动作和终态；确认不会暴露 prompt、凭据或频道内容。无记录时应明确覆盖/权限边界，而非猜测。
- **收益**：把 recurring delivery 的诊断从频道文案提升到可审计证据，降低错误归因与盲目 retry。

## 2. 评估 `openclaw commitments` 作为人工跟进的只读收件箱
**优先级：中｜风险：低（先只读）**

- **能力**：`openclaw commitments` 可列出推断出的 pending/sent/dismissed/snoozed/expired follow-up，并可按 agent 或 JSON 查询。
- **场景**：跨频道存在需要 Luna 决策的事项（如 token、访问授权、发布许可），当前主要依赖日常摘要与 TODO，容易与 cron 噪声混杂。
- **建议**：先在主会话运行只读 `openclaw commitments --all --json`，抽样核对是否准确反映已明确的人工待决项；不要自动 dismiss、snooze 或外发提醒。
- **验收**：待办来源和状态可解释、没有把系统噪声误报为对人的承诺；确认能与现有 TODO 去重。
- **收益**：若精度可接受，可形成一份更清晰的“等待人类决定”视图，避免高频 cron 淹没关键跟进。

## 暂不采用
- **不为 v2026.7.1-2 立即升级。**该修复有价值，但当前没有官方插件更新失败；保持运行稳定，放到下一个插件维护窗口。
- **不自动处理 commitments。**推断机制先以只读准确性验证，避免因误判静默关闭或催促真实的人类决策。
