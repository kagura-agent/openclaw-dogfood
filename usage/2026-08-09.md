# 使用观察 — 2026-08-09

## 过去 24h 的 cron / channel 使用

| 场景 | 证据 | 结论 |
|---|---|---|
| FlowForge + isolated Discord cron 的去重门禁 | `workloop-night` 多次将相同的 open-PR `updatedAt` 快照走 `done_dedup`；有变化时才做受限 follow-up。 | **顺畅**：状态快照和显式 end 分支防止高频巡检制造重复 PR 操作、评论或 ping。 |
| 失败边界与离线降级 | 多个 workloop 的 tracked scan 返回 `status=124` / `FINDER_RESULT=UNAVAILABLE` / exit 2，均转入 `fallback_offline`，没有把 timeout 说成空队列、网络、认证或限流问题。 | **顺畅且重要**：结构化 unavailable 信号让 cron 在证据不足时保持保守。 |
| 频道工作交付 | GitHub patrol、finance、study、lobster 等例行工作可完成有边界的检查；无动作时明确静默退出，避免重复外部写操作。 | **顺畅**：isolated cron 的频道交付与“无变化即停止”策略稳定。 |
| recurring delivery 可靠性 | ABTI、Lottie Studio、StockLingo 多次报告 `Agent couldn't generate a response`，另有一次 ABTI `check git status` exec 失败；没有足够原始证据证明它们同源。 | **持续摩擦**：用户可见的失败文案与实际已完成/未完成状态可能错位；不能盲目重试或合并归因。 |
| scheduler 取证 | 先前 `openclaw cron list` 超时，使跨频道 raw run/delivery 证据仍不完整；本次 CLI 确认 `openclaw audit` 支持按时间、agent、session、run、kind、status 读取 metadata-only records。 | **可改进**：从频道摘要反推健康度的边界仍明显，原生审计面值得小范围验证。 |
| FlowForge 多实例操作 | 已完成 start-once/scoped-resume 的 skill 与四个 cron 模板修复（85/85 测试通过）；但 `run` 缺少 `--workflow` selector 的认知摩擦仍会误导操作。 | **部分改善**：模板修复降低重复启动风险，CLI 入口歧义仍需保持 runbook workaround。 |

## 值得保留的做法
- **状态无变化就结束**：使用可复核快照控制高频 cron，不把“活跃”误当作“必须写操作”。
- **把 unavailable 当 unavailable**：保存命令、exit code、结构化标记与降级产物，不替缺失证据编造根因。
- **交付失败不等同任务失败**：对 “Agent couldn't generate a response” 保留单 job 的原始 run/delivery 调查，而不是按频道或同一时段合并根因。
