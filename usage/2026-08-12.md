# 使用观察 — 2026-08-12

## 过去 24h 的 cron / channel 使用

### 审计证据与覆盖边界
- 从 Kagura 可见的 active/recent session ledger 抽样到 workloop、Cove、study、finance、code-review、GitHub inbox、evolution、server-health、memory-eval、邮件和社区巡检等 cron；各项最新报告均包含明确产物、只读检查或安全停手理由。
- `daily-review` 已基于原始 scheduler 导出确认 **8 个 error-status jobs**；其中 Memory Dreaming Promotion 的上次计划执行是 gateway restart 中断，后续手动执行已成功。因此不把“有 error 状态”直接等同于“任务逻辑未运行”。本 cron 只能读取自己 owner 范围的 Gateway job list，故不声称全局零失败。

## 顺畅的功能 ✅
- **隔离 cron 与 Discord 投递仍是主力工作流。**#github-contribution、#cove、#study、#finance、#code-review、#github-inbox 和 #server-health 在窗口内都产出可追溯报告；例如 finance 发布了带数据源和抓取时间的美股收盘速报，code-review 写入并推送了追踪统计。
- **安全边界在高频自动化中有效。**GitHub patrol 对需要外部沟通/关闭的事项保留人工授权；贡献 finder 不可用时保留离线证据，而非把不完整结果误判为空或启动猜测性改动。
- **任务级去重有实效。**workloop-night 在 21 个 open PR 快照无变化时按去重分支结束，避免重复执行；daily-audit 也清理了一个卡在 `file-issues` 的 zombie FlowForge 实例。

## 摩擦与 workaround ⚠️
- **贡献候选扫描仍会超时。**最新 workloop 的 tracked scan 返回 `FINDER_RESULT=UNAVAILABLE`（exit 2）。现行 workaround 正确：记录离线证据、明确标为不可用而非空队列、禁止基于局部结果进行外部写入。
- **错误状态缺少可操作的分层视图。**daily-review 当前列出 8 个 error-status jobs，原因混合了 gateway restart、模型未生成响应、edge-tts pipeline、文件编辑失败与 model-call timeout；需要按 run history 区分“已恢复的一次性中断”和“连续失败”，而不是统一重跑。
- **外部信息源可用性不一致。**GTM cron 遇到 Reddit 403 与 `web_search` disabled/no-provider，因此安全地以“受限、无新发现”结束；应继续将覆盖缺口和无结果分开报告。
- **记忆检索的宽泛查询仍偏旧。**memory-eval 观察到具体实体+独特事实检索可靠，但宽泛/历史修复查询容易命中陈旧日志或 dreaming 重复文本；workaround 是先用精确路径 `memory_get` 或带日期/实体限定的 `memory_search`，不将单次宽泛命中当作当前事实。
