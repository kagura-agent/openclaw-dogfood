| 场景 | 证据 | 结论 |
|---|---|---|
| Discord 隔离 cron + FlowForge | `memory/2026-08-08.md` 记录 `daily-review #7789`、`github-patrol #7800`、`study #7801/#7807`、workloop 等在各自频道完成；夜间多次 PR 快照无变化时按门禁停止，没有制造 ping、回复或代码变更。 | **顺畅**：isolated cron 的频道交付与显式工作流状态适合高频、低变动的巡检。 |
| 去重与证据边界 | workloop finder 多次输出 `FINDER_RESULT=UNAVAILABLE` / exit 2（tracked scan timeout）；运行均进入 offline fallback，而非把局部文本当候选或诊断未经证实的根因。 | **顺畅且重要**：结构化失败状态能阻止 cron 为“有产出”而编造工作。 |
| 运行/工具记录可读性 | `openclaw audit --help` 显示可按时间、agent、session、run、状态读取 bounded 的 metadata-only agent-run 与 tool-action records；当前日常巡检主要依赖频道摘要与 daily memory。 | **可改进**：原生 audit surface 可补足跨频道复盘的直接证据，减少从摘要反推。 |
| scheduler 全局可见性 | 今日 daily-review 的 `openclaw cron list` 在 30 秒后 GatewayTransportError；这个 isolated run 也不据局部可见性宣称其他频道 scheduler 全部健康。 | **持续摩擦**：缺少目标 job 的 raw run/delivery 证据时，只能报告查询边界，不能归因或全局化。 |
| FlowForge 多实例入口 | 本轮在多个实例并存时，`flowforge run daily-audit` 报多 active instances；`run` 没有 `-w`，但 `status --workflow` 和 `next --workflow` 可明确定位。 | **摩擦，有 workaround**：先读取 workflow 状态再用支持 `--workflow` 的推进命令；`run` 的选择接口仍容易误导。 |

## 值得保留的做法
- **状态未变即停止**：以可复核的 PR `updatedAt` 快照决定是否继续，避免定时任务重复进行外部操作。
- **把 unavailable 当 unavailable**：保留命令、exit code 与结构化标记；不把 timeout 解释成空队列、认证问题或网络根因。
- **限定观察范围**：不能取得其他 job 原始 history 时，只报告本 run 与现有记录，不把局部视图外推为全局 scheduler 健康。
