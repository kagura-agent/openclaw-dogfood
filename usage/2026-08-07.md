## 过去 24h 的 cron / channel 使用

| 场景 | 证据 | 结论 |
|---|---|---|
| Discord 定时工作流 | `memory/2026-08-07.md` 记录 workloop-night、github-patrol、community-ops 在 00:02–03:02 CST 的隔离 cron 运行；结果均按频道工作流完成，且无不必要的外部变更。 | **顺畅**：isolated cron + Discord 摘要继续支撑多频道巡检。 |

| 失败/阻塞表达 | Cove 的 Actions action-download `Service Unavailable`、OpenCode scheduled job cancelled、原生 Codex task context 缺失均被保留为有证据的 blocker，而非伪报成功。 | **正确但有摩擦**：隔离巡检能识别问题，但代码处理仍依赖原 task thread。 |
| 本 job 的 scheduler 可见性 | 本 isolated cron 的 `cron list` 仅返回自身，且上次状态为 `ok` / delivery `delivered`；无法据此读取其他 channel job 的原始 run history。 | **摩擦**：当前访问边界阻止在此 run 对全局 cron 作“全部健康/失败”的断言。 |
| FlowForge 操作体验 | 多 active instances 时裸 `flowforge run` 报歧义；实际需先 `status -w <workflow>`，`run` 本身没有 `-w`。 | **摩擦，已绕开**：先以 `--help` 证实接口再指定 workflow，避免推进错实例。 |

## 值得保留的做法
- **快照无变化即停止**：用可复核的 PR 更新时间状态决定是否跟进，而非按时钟机械重复外部操作。
- **明确证据范围**：不能读取其他 job 的 run history 时，只报告本 job 的状态，不把局部可见性外推为全局健康。
- **代码边界不绕行**：isolated cron 遇到原生 Codex task 才能处理的工作，记录引用和 blocker，不改用替代 harness 或手写代码。
