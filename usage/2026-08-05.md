# 使用观察 — 2026-08-05

## 过去 24h 的 cron / channel 使用

| 场景 | 观察 | 结论 |
|---|---|---|
| Discord cron delivery | `cove-patrol`、`channel-patrol`、`study-loop`、`auto-trader` 等均有可见投递；巡检摘要能汇总多频道状态。 | **顺畅**：isolated cron → Discord delivery 可用。 |
| Study + FlowForge | `study-loop` 完成 cMCP 深读、归档与 08-19 复查；本次日报也以 FlowForge `daily-audit` 入口执行。 | **顺畅**：工作流约束能保留验证与记录步骤。 |
| GitHub/workloop | night patrol 记录 finder `SIGKILL` 后采用 offline fallback，没有把失败包装成完成。 | **顺畅**：失败边界与 fallback 记录清楚。 |
| Channel patrol | 能聚合 server-health、study、finance、code-review、mail 等频道的新状态。 | **顺畅**：跨频道可观测性强。 |
| Finance auto-trader | 任务停在缺少 `trade_plan_builder_skill` 的安装范围确认，未绕过金融执行门禁。 | **正确但有摩擦**：安全门禁有效，但会让定时任务重复停在同一等待点。 |
| Cove task heartbeats | 多个 task session 只回复 `HEARTBEAT_OK`/`NO_REPLY`；另有记录指出 Cove session 的 task-update/message 能力被 policy 过滤。 | **摩擦**：任务状态的“要求更新”与实际可用写入工具不一致，需先修工具注入/策略。 |
| 本 version-check cron | scheduler 显示上一轮 `lastDeliveryStatus=not-delivered`，错误为 provider 拒绝 request schema/tool payload；本轮能够正常执行。 | **摩擦**：cron 的失败字段缺少可操作细节，且 delivery schema 兼容性需持续观察。 |

## 值得保留的做法
- **先核验再汇报**：Cove patrol 明确核对 PR 的 CI、review comments 与 mergeability；workloop 对失败的 clone/finder 保留证据与边界。
- **按门禁停下，而不是猜测绕过**：auto-trader 在缺 skill 时请求安装范围，没有生成未经许可的交易动作。
- **避免为指标伪造使用**：daily audit 没有为了“使用 meme”而跨频道发送消息；但自然对话中仍应按偏好适度使用。
